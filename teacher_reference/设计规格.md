# 法律庭审 Benchmark 改造：设计规格（两个 agent 共用）

版本：2026-10-19 · 主控撰写。两个 agent 各负责一道题（003 或 004），都必须遵守本规格。

---

## 0. 背景

**原交付**：`00_共享/原始交付_只读/法律实验交付_003_004/`（只读）。两道题：
- CA-PILOT-003，题源 People v. Moore（加州内华达县高等法院上诉庭，AP14-0020，2015）
- CA-PILOT-004，题源 People v. Munoz (2006) 138 Cal.App.4th 860

**上一轮审查**：`00_共享/上一轮评估/`
- `法律Benchmark评估报告.pdf`（26 页），以及它的纯文本版 `评估报告_纯文本.txt`
- `庭审全过程回放.html`：8 场原始运行的逐条回放
- `data.json`：8 场原始运行的全部事件、陪审团记录、评分和统计
- `复现脚本/`：解析原交付的脚本，可以参考它们怎么读原始记录

上一轮的结论，一句话：**引擎扎实，但题目内容撑不起真实律师工作**。
- 案件世界只来自判决书里的几段话：003 只有 16 条事实，004 只有 17 条。
- 调查服务对任何请求都返回同一段写死的文字。
- 证人只能从 1–9 句预写的话里挑。003 的 44 次证人回答里，31 次是"来源未记载"。
- 检察官不对抗：8 场的结案陈词都承认证据不足。
- 两轮之间没有新信息。
- 8 场 20 项罪名全部无罪，而两案历史上全部定罪。
- 评分：85%–99%。庭前 12 项人人满分；写好的"不适用"条款没有执行；GPT 没读事实材料，"实际核读文件"照样满分。

**用户这次的要求（原话）**：
> 在这两道真实的题目的基础上，首先把庭前准备这个事情做真实，然后真实庭审也做真实，不要像现在这样很莫名其妙。然后真实之后就希望这两个模型的分数降下来。因为真实庭审会有很多细节的小问题。

用户心中的律师工作流：接案 → 整理案件 → 获取更多材料、处理文件 → 带着材料上庭陈述、和对方律师辩论 → 回去继续搞材料 → 再上庭。每道题提供环境和若干其他角色。

**"这两个模型"**指两个候选辩护律师：GPT（gpt-5.6-sol）和 Seed（doubao-seed-evolving）。模型分配和接口见 `API接入说明.md`。

## 1. 诚信红线（必须遵守，违反任何一条都会让整个结果作废）

1. **分数下降必须来自真实难度，不是刁难。**
   - 评分标准必须在任何候选模型正式运行之前写好并冻结（记录 sha256 和时间）。
   - 冻结后只允许修 bug。每次修改都写进 `rubric/rubric_changelog.md`：原因、改了哪几项、是否对已有运行全部重评。
   - 不准根据候选模型的具体输出，新增专门针对它的扣分项。
   - 环境（世界、机制、陷阱脚本）也在正式运行前冻结，规则同上。
2. **可达性。** 必须写一条"参考辩护路径"：一串脚本化的动作，只使用环境里合法可得的动作和信息（不能偷看隐藏世界），在环境里实际跑通，得分应 ≥ 85%。用它证明满分可达，题目不是故意做成做不到。
3. **区分度。** 必须跑一个"弱辩护基线"：脚本化，只做最低限度的动作。它的得分应明显更低（参考值 ≤ 40%），判决结果也应比参考路径差。如果两者分不开，说明题目没有校准，要改世界或机制（仍在冻结之前）。
4. **法律来源必须真实。**
   - 所有法条、判例、陪审团指示（CALCRIM）都必须来自可核实的官方或权威来源，例如 leginfo.legislature.ca.gov、CourtListener、courts.ca.gov、justia 的法条历史版本。
   - 每条保存 URL、检索日期、sha256。禁止编造判例、引文或页码。
   - 注意适用时间：模拟庭审发生在原案审理的时间（003 约 2013–2014 年，004 约 2003–2004 年）。晚于这个时间的判例或法条修订，不得作为"当时有效的法律"提供。可以放进检索库当干扰项，但必须如实标注日期。
5. **事实分两类，逐条标注。**
   - `anchor`：判决原文里已有的事实。必须保留、不得矛盾，附原文段落定位（沿用原交付的 `CL-O<id>-P<nnnn>` 格式）。
   - `authored`：为了让庭审真实而补写的细节。必须与 anchor 一致，内部前后一致，符合当时当地的真实做法。
   - 不得把 authored 事实说成历史事实。
6. **人名一律用化名。** 判决里的真实人物（被告、被害人、警员、律师、证人）不得用真名。我们会给他们补写大量虚构细节（用药、资质、陈述不一致等），不能安到真人头上。所有人名都用虚构化名，并在 README 里写明"人物为化名，补写事实为虚构"。
7. **如实报告。** 分数没有下降，或者下降来自工程问题（格式、超时、预算）而不是法律能力，都要如实写明。
8. **任何文件、日志、报告里都不得出现 API key。**

## 2. 真实性要求

### 2.1 案件世界

- **隐藏世界远大于初始卷宗**：参考规模 150–300 条事实、20–40 份文件。律师开局能看到的不超过三成。
- **文件是真实形态的**，按题目选用，例如：
  - 起诉书或控告书；警方报告（警员叙述，带时间戳）；CAD/911 记录与录音转写；执法记录仪转写
  - 药物影响评估表（DRE / drug influence evaluation）；化验报告与监管链；警员培训和资质记录
  - 租约或其他居住证据；药房记录；医疗记录
  - 照片辨认表（six-pack 与签字的辨认告知书）；侦查员笔记；现场照片说明与测量
  - 先前证言、预审笔录
- **文件之间要有真实世界常见的不一致**：时间对不上、措辞不同、有遗漏。
- **事实对双方都有利有弊**。不能让辩方轻易全胜，也不能让控方稳赢。经过校准后，结局要随辩护水平变化（见 1.3）。

### 2.2 庭前准备（用户要求先做这一块）

- **证据开示（discovery）**
  - 控方有自己的卷宗。开局交付一个初始开示包。
  - 辩方可以按 Penal Code §1054.1 等提出具体的开示请求：请求越具体，越容易拿到。控方可以合理拒绝（超出范围、需要法院令等）。
  - 有些材料要走正当程序。警员人事和投诉记录要提 Pitchess 动议（Evidence Code §§1043、1045，按当时版本），并有法院审查。第三方记录（药房、医院、电话公司）要发传票（subpoena duces tecum），经法院审查。
  - 控方可能迟交材料，辩方需要相应处理：申请延期、请求排除、请求指示等。
- **调查**
  - 辩方调查员可以去现场测量、找证人谈话（证人可以拒绝）、调取公开记录。
  - 调查结果取决于请求本身：请求命中某份文件的触发条件，才返回该文件；过宽或无关的请求，返回"没有具体结果"并说明原因。同一服务，不同的请求必须可能得到不同的结果。
  - 返回的内容只能来自隐藏世界里已有的文件和事实，不得现场生成新事实（沿用并升级 fact_id 校验）。
- **会见当事人**
  - 被告有丰富的记忆（参考 30–60 条），包括对辩方有利的、不利的、以及他本人想隐瞒的事实。
  - 被告可能一开始说谎或隐瞒，被具体证据追问时才承认，这是真实的。
  - 涉及职业伦理的情况（例如当事人坚持要作伪证），要按当时的加州职业规范和判例来处理。
- **专家**
  - 可以聘请专家（毒理/DRE、目击证人辨认等）。专家只根据律师提供的材料和问题给意见，给什么、问什么决定意见的质量。
  - 专家意见可能部分不利。聘请有成本。
- **法律检索**
  - 检索库要大于本题需要的法律，包括干扰项、过时版本、后来被推翻或晚于审理日期的判例。律师必须自己检索和筛选。
  - 提供真实可用的检索工具：关键词检索 + 全文阅读。
- **资源约束**
  - 庭前有时间或预算上限（例如以"小时"计），每个动作消耗时间，迫使律师取舍。
  - 上限要让参考路径够用，但不够把所有事都做一遍。

### 2.3 庭审（两轮）

- **第一轮：真实的庭前听证。** 有证人当庭作证、交叉询问、法官当庭裁定。
  - 003：可以是排除陈述的 Miranda / Evidence Code §402 听证，加上其他审前动议。
  - 004：可以是对 B 的条件讯问（conditional examination，Penal Code §1335 以下），或者辨认证据可采性听证。
- **两轮之间：必须有真实的新信息**，律师要回去调查、补材料、调整策略。例如：迟到的开示材料、化验结果出来、证人的新陈述、第一轮当庭证言暴露的新线索。
- **第二轮：陪审团审理**，依次包括：
  1. 开场陈述
  2. 控方举证（主询问、交叉询问、再主询问）
  3. 控方举证结束后，辩方可以提 Penal Code §1118.1 无罪判决动议
  4. 辩方举证，包括是否让被告作证的决定
  5. 反驳证据
  6. 陪审团指示会议：双方提出或反对 CALCRIM 指示
  7. 结案陈词：控方、辩方、控方反驳
  8. 法官向陪审团宣读指示
  9. 陪审团评议与裁决：建议 3–6 名陪审员各自评议后投票，需要一致，可能出现僵局
- **检察官**
  - 有自己的卷宗和定罪目标，在职业伦理范围内尽力定罪：为证据打基础、准备证人、提出异议、交叉询问辩方证人、结案时请求定罪、回应辩方论点。
  - **不得**设定为"客观回应缺口"那种中立角色。
- **法官**
  - 按法律裁定：要求具体的异议理由和 offer of proof；可以警告律师、要求重新提问、给出限制性指示。
  - 裁定要与评分标准的法律立场一致，不能出现"环境奖励的做法正是 rubric 反对的做法"。
- **证人**
  - 每人参考 20–60 条记忆，包括先前陈述（可用来弹劾）、偏见、不确定之处、在什么条件下会让步。
  - 回答由模型用自然语言生成，但每个事实性陈述都必须映射到允许的 fact_id，由校验器检查，不得出现新事实。
  - 可以回答"是/否"。
  - 对诱导问题、复合问题、开放式问题有真实的反应。开放式的交叉询问可能引出对辩方不利的内容，这是真实的陷阱。
  - 证人不会同意与世界事实矛盾的命题。
- **固定的庭审事件脚本（机会点和陷阱）**
  - 为了让不同运行可比，环境里要预设一批"一定会出现"的事件。例如：
    - 控方在专家基础没打好之前，就问警员结论性意见；
    - 证人主动说出不可采的品格证据；
    - 控方在结案中作出不当陈述，例如评论被告沉默（Griffin 错误）或曲解合理怀疑。
  - 辩方必须及时、具体地提出异议并请求补救，否则按 Evidence Code §353 视为放弃。
  - 这些事件要真实，是实际庭审中常见的情况，并在 rubric 里有对应的检查项。
- **协议摩擦不吃预算**
  - 格式错误或非法动作，返回清楚的错误信息，允许重做一次，不扣行动次数。
  - 工具命名不得有歧义，不要再出现原交付里 `request_examination` 那种"名字像申请询问证人、实际是调查别名"的情况。

## 3. 评分

- **规模**：参考 60–120 项，覆盖庭前（开示、调查、会见、专家、检索）、第一轮、两轮之间、第二轮各个环节的细节。
- **每项写清**：检查什么；对应哪个事件、文件或事实；0/1/2 分各自的锚点；触发条件；"不适用"条件。
- **"不适用"必须真正生效**：机会没出现，记 N/A，从分母中剔除；同时报告原始分母和适用分母。有固定事件脚本以后，大部分项每次运行都适用。
- **能用脚本判的，必须用脚本判**。例如：是否提出了某项开示请求；是否在 N 个事件内对某个预设陷阱提出异议；引用某份文件之前是否真的读过它；是否引用了晚于审理日期的判例。需要判断质量的项，才用模型评分。
- **双评分器**：主评分 gpt-6-sol，副评分 doubao-seed-evolving，effort 都是 high。报告各自的分数和一致率，把分歧大的项列出来。
- **结局分**：裁决结果可以占一小部分，参考 ≤ 10%。
- **严重错误**单独列出并扣分，例如：编造事实或法律；违反法院裁定、提及已被排除的证据；在交叉询问中用开放式问题引出致命事实；诱导当事人作伪证；不必要地承认控方要件；错过必须当庭提出的异议。
- **运行次数**：每个候选模型每题至少正式跑 2 次，预算允许就跑 3 次，报告均值和范围。

## 4. 模型与接口

见 `API接入说明.md`，已实测可用。两道题统一如下：
- 候选辩护律师：gpt-5.6-sol 和 doubao-seed-evolving，effort 都是 medium（与原交付相同，便于对比）。

- 每个请求必须显式传 `instructions`（原因见 API 说明里的"重要的坑"）。

## 5. 预算与工程约束

- **token 预算**
  - 每次运行 ≤ 30M tokens。
  - 单次调用的上下文 ≤ 150K tokens。超过时压缩历史，但不得让律师丢失他可见的正式记录：用"律师笔记 + 可检索的记录"代替整段塞入。
  - 每道题总计（开发 + 校准 + 正式运行 + 评分）≤ 200M tokens。
  - 建 `usage_ledger.jsonl` 记录每次调用。快要超出预算时，先停下，在 `进度.md` 里说明。
- **并发**：每个 agent 同时最多 3 个 API 请求；遇到 429/5xx 用指数退避重试。
- **基于原运行环境改造**
  - 先把 `00_共享/原始交付_只读/法律实验交付_003_004/第00X题/04_运行环境` 复制到你自己的目录再改。原交付里"现有 V9 入口仍依赖原运行目录"，复制后要自己理顺入口。
  - 保留原有的优点：阶段状态机；按角色的可见范围；披露、采纳、限定用途三者分开；陪审团只看准入的记录；fact_id 校验；哈希链日志；版本化文件；回放。
  - 可以大幅重构，但要有自动化测试，至少包括：
    - 用离线 mock 跑通全流程；
    - 调查服务对不同请求返回不同结果；
    - 证人回答通过 fact_id 校验，编造的事实会被拦下；
    - "不适用"在评分里生效；
    - 非法动作不扣行动次数。
- **事件日志格式与原交付兼容**：`author_events.jsonl`，字段为 `event_id, stage_id, round, kind, actor, text, references, audience, meta`。新增的 kind 写进 `engine/接口说明.md`。这样主控可以复用回放页面。
- 只在自己的目录里写文件。`00_共享` 是只读的，另一道题的目录不要碰。


## 7. 工作顺序（先庭前，后庭审）

1. **读。** 上一轮评估报告；原交付该题的全部材料；判决原文全文；相关的真实法律。写出"该题真实诉讼的工作清单"：真实的辩护律师在这个案子里会做哪些事。
2. **写案件世界。** 先 anchor，再 authored。包括双方卷宗、证人记忆、被告记忆、可调取的文件及其触发条件。
3. **实现庭前准备的真实机制**：开示、调查、会见、专家、检索、资源约束。单独测试。
4. **实现两轮庭审的真实机制**：第一轮听证、两轮之间的新信息、第二轮陪审团审理、固定事件脚本、对抗性检察官、多名陪审员。
5. **写评分标准并冻结**，同时写好脚本检查。
6. **校准**：弱基线和参考路径各跑 1 次。可以据此调整世界或机制，但必须在任何候选正式运行之前完成，并重新冻结。
7. **正式运行**：GPT ≥ 2 次，Seed ≥ 2 次。
8. **评分与汇总**：双评分 + 脚本检查；汇总；与原交付分数对比（003 原：GPT 87/92、豆包 79/92；004 原：GPT 74/80、豆包 79/80）。注明新旧 rubric 不同，比较的是"在更真实的题目上的表现"。
9. **写 README.md。**

## 8. 汇报方式

- 每完成一步，更新 `进度.md`。
- 遇到需要用户拍板的设计取舍，写进 `进度.md` 的"待决问题"，然后按最合理的默认继续，不要停下来等。
- 完成时，最终回复里给出：改动摘要；关键数字（参考路径、弱基线、GPT、Seed 的分数；均值和范围；两个评分器的一致率）；预算使用；已知局限。
